# Property Finder — сохранность загрузок в production

## Что реализовано
CarrierWave 3.1.4 сохраняет исходное изображение и thumbnail в `public/uploads`. Для локального development это обычная файловая система. Для test используется отдельная директория `tmp/property_finder_test_uploads`. Никакие существующие каталоги, изображения или записи БД не удалялись.

Для production добавлена защита: **перед записью медиа** приложение требует корректный путь постоянного монтирования и права на запись. Иначе загрузка отклоняется, чтобы пользователь не получил ложное подтверждение, после которого файл исчезнет при redeploy.

## Railway — один инстанс, volume
1. В **отдельном** сервисе Property Finder на Railway добавить Volume с mount path **точно** `/app/public/uploads` (без пробелов). Не использовать объем другого проекта или `postgres-volume`.
2. Railway предоставляет `RAILWAY_VOLUME_MOUNT_PATH` при запуске контейнера. Приложение сверяет его с реальным ожидаемым `Rails.root/public/uploads` и проверяет writable. Для другого хостинга можно использовать `PROPERTY_FINDER_UPLOADS_VOLUME_MOUNT` как явно настроенное указание фактического mount path; наличие volume нужно подтвердить у провайдера.
3. В production потребуется раздача `/uploads` из `public` — проверить `RAILS_SERVE_STATIC_FILES` и статические URL. Не отключать сохранение uploads при миграции с прежнего деплоя; заранее перенести/сохранить оригиналы и thumbnails.
4. После деплоя провести подтвержденный тест: авторизованный агент загружает тестовое PNG, открывает исходник и thumb; перезапустить/передеплоить **только новый Property Finder service**, убедиться, что оба файла и строка БД сохранились. Реальные клиентские данные/фото не использовать для теста.
5. Включить резервное копирование volume и PostgreSQL по отдельности. Наличие volume само по себе **не означает** наличие проверенного восстановления.

`RAILWAY_VOLUME_MOUNT_PATH` задает Railway, а не клиент/браузер. Загрузка при неверной конфигурации завершится ошибкой, а не молча сохранит файл на временном диске. Работать с сервисом в production можно только после подтверждения пункта 4.

## Границы
- File storage на отдельном Railway Volume — разумен для одного инстанса и небольшого портфолио; для масштабирования на много инстансов позднее лучше S3-совместимое object storage с явно проверенными URL, правами и резервированием.
- `public/uploads` содержит legacy-файлы, уже отслеживаемые историческим Git. Их нельзя массово удалять, очищать, перемещать или перезаписывать без отдельного бэкапа и согласования. Новые файлы игнорируются Git.
- 5 МБ, JPEG/PNG и MiniMagick thumbnails уже реализованы; проверку размера/формата нужно повторно подтвердить в браузере.
- Текущая конфигурация test не является production-копией; непрерывность работы при redeploy пока **не подтверждена**.
